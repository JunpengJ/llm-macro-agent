# 异常检测与补充检索

> 本文档描述项目中异常数据检测与自动补充检索机制的设计思路。具体阈值、关键词、评分规则等核心机密不在本文档范围内。

---

## 一、为什么需要异常检测

在自动化分析系统中，**数据异常与信息滞后的矛盾**是一个常被忽视但影响巨大的问题。

| 问题 | 表现 | 后果 |
|:---|:---|:---|
| **异常数据被默默略过** | 关键指标突然大幅变动，但简报未解释 | 分析结论建立在未解释的前提上 |
| **信息搜索滞后** | 重大事件先反映在数据上，新闻报道滞后 | 分析系统"看到数据，不知道原因" |
| **搜索路径单一** | 常规关键词搜索无法覆盖突发情况 | 重大事件被漏掉 |
| **异常归因偏差** | LLM 用旧信息强行解释新异常 | 结论误导下游 |

**核心矛盾**：数据是即时的，信息是滞后的。如果不主动弥补这个时间差，系统会输出"数据准确但解释错误"的报告——这比"数据错误"更危险，因为它看起来是对的。

## 二、异常检测机制

### 2.1 检测维度

系统对以下核心指标进行异常检测：

| 维度 | 检测对象 |
|:---|:---|
| **能源** | 原油价格 |
| **贵金属** | 金价、银价 |
| **利率** | 中长期国债收益率 |
| **汇率** | 主要货币对 |
| **权益** | 主要股指 |
| **信用** | 信用利差 |
| **流动性** | 银行间市场指标 |

### 2.2 检测标准

以**单日变动幅度**为核心判据（具体阈值在配置文件中维护，不在此文档披露）。

**抽象原则**：

- 不同指标使用不同阈值（波动性大的指标阈值高，波动性小的指标阈值低）
- 检测相对变动（百分比），不检测绝对变动
- 检测单一指标，也检测指标间的联动异常

### 2.3 检测时机

```
每日简报生成完成后
    ↓
系统自动比对：当日快照 vs 前一基准
    ↓
识别超阈值变动指标
    ↓
检查简报中是否有对应解释
```

**关键设计**：检测在**简报生成之后**，而非之前。原因：

- 简报生成时已有完整信息
- 可以在简报输出后做"是否解释充分"的判断
- 避免检测结果影响简报生成的中立性

## 三、补充检索机制

### 3.1 触发条件

异常检测发现"**有异常 + 无解释**"时，触发补充检索。

**判断逻辑**：

```
异常指标存在
    │
    ├─ 简报中有明确解释 ──▶ 不触发
    │
    └─ 简报中无解释或无充分解释 ──▶ 触发
```

**"无解释"的定义**：

- 简报中未提及该指标的变动
- 简报中提及但未给出原因
- 简报中的原因属于旧闻重提，无法解释当日变动

### 3.2 检索任务生成

系统自动生成补充检索任务，任务包含：

| 字段 | 内容 |
|:---|:---|
| **异常指标** | 哪个指标异常（不写具体数值） |
| **变动方向** | 上升/下降 |
| **时间窗口** | 变动发生的时间范围 |
| **建议关键词** | 系统根据指标类型生成2-3个关键词 |
| **检索目标** | 寻找该指标变动的直接触发事件 |

**关键设计**：**关键词由系统生成，而非LLM自由发挥**。系统维护"指标-关键词"映射表，保证检索的确定性和可复现性。

### 3.3 检索执行

```
补充检索任务
    ↓
选择专项搜索实例（按指标类型匹配）
    ↓
执行补充搜索
    ↓
搜索无结果 ──▶ 记录"无法归因"，维持原简报
    ↓
搜索有结果 ──▶ 进入事实核查
```

**降级路径**：

- 首次搜索无结果 → 换搜索实例重试
- 二次搜索仍无结果 → 记录"异常待归因"，不阻塞主流程

### 3.4 二次核查

补充搜索结果**必须经过事实核查**，与主流程同等标准：

- 分级标注
- 矛盾识别
- 时效核验
- 信源盲区标注

**关键设计**：**不因为"补充"就降低核查标准**。补充信息如果未经核查，会污染主流程。

### 3.5 简报合并

核查后的补充结果与原始简报合并，触发**第二次简报生成**：

```
原始简报 + 补充核查结果
    ↓
第二次简报生成
    ↓
输出最终简报
```

**合并规则**：

- 补充信息作为独立章节加入简报
- 原简报中"异常待归因"的标注被替换为具体归因
- 补充信息仍按分级标准使用

## 四、与主流程的集成

### 4.1 流程位置

```
主流程：
    搜索 → 核查 → 简报 → 分析 → 基线更新

异常检测插入点：
    简报生成后、分析开始前
    ↓
    异常检测
        ↓
        正常 ──▶ 进入分析
        ↓
        异常 ──▶ 补充检索 → 二次核查 → 二次简报 → 进入分析
```

**关键设计**：异常检测**不阻塞主流程**，仅在有异常时插入。

### 4.2 与 Agent 层的关系

| 阶段 | 使用的 Agent |
|:---|:---|
| 常规搜索 | 全部搜索实例 |
| 补充搜索 | 专项搜索实例（按指标类型匹配） |
| 补充核查 | 同一个核查 Agent |
| 二次简报 | 同一个简报 Agent |

**关键设计**：**复用现有 Agent，不新增 Agent 类型**。避免 Agent 数量膨胀。

### 4.3 与分层记忆的关系

| 场景 | 与记忆的交互 |
|:---|:---|
| 检测到异常 | 检索索引记忆，看是否曾出现类似异常 |
| 补充检索到历史内容 | 临时注入活跃记忆（本轮内），不改变长期状态 |
| 异常处理完成 | 记录到当日状态，随基线更新进入活跃记忆 |
| 异常持续出现 | 升级到"规则级"问题，触发框架更新流程 |

## 五、异常处理的状态机

```
        ┌──────────┐
        │  正常态  │
        └────┬─────┘
             │ 检测到异常且无解释
             ▼
        ┌──────────┐
        │ 待补充态 │
        └────┬─────┘
             │ 补充检索
             ▼
        ┌──────────┐
        │ 补充中态 │
        └────┬─────┘
             │
     ┌───────┴───────┐
     │               │
     ▼               ▼
┌─────────┐    ┌──────────┐
│ 归因完成 │    │ 无法归因 │
└────┬────┘    └────┬─────┘
     │              │
     ▼              ▼
┌─────────┐    ┌──────────┐
│  恢复常态 │    │ 待下次触发│
└─────────┘    └──────────┘
```

**状态说明**：

| 状态 | 含义 | 处理 |
|:---|:---|:---|
| **正常态** | 无异常或无未解释异常 | 按主流程执行 |
| **待补充态** | 检测到异常，准备补充检索 | 生成检索任务 |
| **补充中态** | 补充检索执行中 | 等待结果 |
| **归因完成** | 补充信息已核查并合并 | 进入分析阶段 |
| **无法归因** | 补充检索无结果 | 标注"待归因"，不阻塞 |

## 六、关键设计决策

### 决策 1：为什么在简报后而非简报前检测

**背景**：如果在简报生成前检测，简报可能会"为了解释异常而编造原因"。

**决策**：简报后检测，简报保持中立，异常检测独立进行。

**收益**：简报质量和异常检测质量都有保障。

### 决策 2：为什么关键词由系统生成

**背景**：如果让 LLM 自由生成关键词，检索的确定性无法保证，也不可复现。

**决策**：系统维护"指标-关键词"映射表，保证检索的确定性和可复现性。

**收益**：检索过程可控，结果可审计。

### 决策 3：为什么补充结果必须二次核查

**背景**：补充搜索的结果质量不确定，如果直接合并，会污染主流程。

**决策**：补充结果必须经过与主流程同等标准的事实核查。

**收益**：补充信息的质量与主流程信息一致。

### 决策 4：为什么不新增 Agent 类型

**背景**：新增 Agent 类型会增加系统的复杂度和维护成本。

**决策**：补充检索复用现有 Agent，仅改变输入参数。

**收益**：Agent 数量可控，维护成本低。

### 决策 5：为什么异常检测不阻塞主流程

**背景**：如果异常无法归因就阻塞主流程，系统会在信息缺失时无法运行。

**决策**：异常检测是"增强"而非"阻塞"。

**收益**：系统鲁棒性提升，信息缺失时仍可输出。

## 七、可靠性保障

### 7.1 检测可靠性

| 保障维度 | 机制 |
|:---|:---|
| **阈值准确** | 阈值在配置文件中维护，不硬编码在代码中 |
| **检测全面** | 覆盖多个核心指标，不只检测单一指标 |
| **误报控制** | 设置合理阈值，避免频繁误报 |
| **漏报控制** | 定期审计，检查是否有异常未被检测 |

### 7.2 检索可靠性

| 保障维度 | 机制 |
|:---|:---|
| **关键词可靠** | 系统生成，非 LLM 自由发挥 |
| **搜索结果可靠** | 必须经过事实核查 |
| **降级可靠** | 检索失败时明确降级路径 |
| **可复现性** | 相同异常下，检索过程一致 |

### 7.3 合并可靠性

| 保障维度 | 机制 |
|:---|:---|
| **信息不丢失** | 原简报内容全部保留 |
| **分级不降级** | 补充信息按原分级标准使用 |
| **冲突有标注** | 补充信息与原简报冲突时明确标注 |
| **可回溯** | 合并过程可追溯 |

## 八、与六层防火墙的关系

异常检测与补充检索是**六层防火墙之上的延伸**：

| 防火墙层次 | 异常检测的角色 |
|:---|:---|
| 数据级 | 异常检测基于数据级校验的比对结果 |
| 逻辑级 | 异常检测结果作为逻辑校验的补充输入 |
| 信源级 | 补充检索的信息经信源级校验 |
| 规则级 | 异常检测不直接触发规则，仅提供背景 |
| 交叉验证 | 补充结果与原信息交叉验证 |
| 熔断 | 异常检测不触发熔断，仅提示 |

**关键设计**：**异常检测不改变防火墙的防护逻辑，仅扩展信息覆盖面。**

---

## 九、适用边界

异常检测与补充检索适用于：

- 自动化分析场景
- 数据实时更新但信息滞后的场景
- 需要高可靠性的场景
- 输出会被下游使用的场景

**不适用**：

- 纯对话场景（无固定数据源）
- 单次运行的系统（无需持续检测）
- 数据与信息同步的场景（无信息滞后问题）
