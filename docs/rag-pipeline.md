# RAG 全链路设计

> 本文档描述项目的检索增强生成（RAG）全链路设计思路。具体数据源、评分规则、阈值等核心机密不在本文档范围内。

---

## 一、为什么需要 RAG 全链路

传统 RAG 系统的常见形态是「用户提问 → 向量检索 → 拼接上下文 → LLM 生成」。这种模式适用于**知识问答**场景，但用于**每日自动化分析**时，会暴露以下问题：

| 问题 | 具体表现 |
|:---|:---|
| **检索时效性不足** | 向量库更新滞后，无法捕捉当日突发事件 |
| **检索结果不可验证** | 召回的文本片段缺乏信源等级，LLM 容易引用低质信息 |
| **单次检索覆盖不全** | 单一检索路径容易遗漏关键事件 |
| **无矛盾识别** | 不同来源的信息矛盾时，LLM 会随意选择或编造 |
| **无降级机制** | 检索失败时整个流程崩溃 |
| **无反馈闭环** | 输出质量无法回溯到检索环节 |

因此，本项目将 RAG 从「单次检索」升级为**全链路工程系统**：搜索、校验、生成、审核四阶段独立，通过标准化接口串联，支持降级、替换、审计。

---

## 二、全链路四阶段

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│   搜索      │──▶│   校验      │──▶│   生成      │──▶│   审核      │
│  Search     │   │  Verify     │   │  Generate   │   │  Audit      │
└─────────────┘   └─────────────┘   └─────────────┘   └─────────────┘
     │                  │                  │                  │
  多源并行          分级核查          结构化输出         规则自检
  实时性优先        矛盾识别          上下文精简         反馈闭环
```

**核心原则**：每个阶段职责单一，输出标准化，可独立测试与替换。

---

## 三、阶段一：搜索（Search）

### 3.1 设计目标

- **实时性**：优先捕捉当日/近几日增量信息，而非历史存量
- **多源并行**：不依赖单一检索路径，避免单点遗漏
- **场景专用**：不同分析维度使用独立搜索实例，避免关键词互相干扰
- **确定性输出**：返回结构化搜索结果，不做主观判断

### 3.2 核心设计

**多实例并行架构**：

```
搜索实例 A（维度1关键词） ─┐
搜索实例 B（维度2关键词） ─┼──▶ 合并原始结果
搜索实例 C（维度3关键词） ─┘
```

每个实例独立配置：
- 专属关键词组
- 专属时间窗口
- 专属信源偏好

**时间窗口约束**：
- 强制限定搜索窗口（如近3天/近5天）
- 超出窗口的信息标注"背景信息，非本周事件"
- 避免旧闻污染当日分析

**事件驱动扫描**：
- 除常规关键词外，强制扫描若干"突发事件领域"
- 突发事件领域用固定关键词组覆盖，不依赖LLM自由发挥
- 扫描结果统一进入下游，不区分对待

### 3.3 输入输出

| 项 | 内容 |
|:---|:---|
| **输入** | 分析任务描述 + 关键词组 + 时间窗口 + 快照基准 |
| **输出** | 原始搜索结果（标题 + 来源 + 发布时间 + 摘要） |

**约束**：搜索阶段不生成结论，不做结构化整合，只返回原始信息。

---

## 四、阶段二：校验（Verify）

### 4.1 设计目标

- **分级标注**：为每条情报标注可信度等级，下游按等级使用
- **矛盾识别**：多源信息矛盾时明确标注，不强制统一
- **时效核验**：识别超出窗口或时间不明的情报
- **全覆盖**：不对情报做取舍，仅做分级

### 4.2 核心设计

**分级标准**（抽象版）：

| 等级 | 含义 | 下游使用 |
|:---|:---|:---|
| L1 | 权威来源可确认 | 可直接使用 |
| L2 | 权威来源报道，无矛盾 | 方向性参考 |
| L3 | 单一来源或存在矛盾 | 需人工判断 |
| L4 | 与权威数据矛盾 | 不得使用 |

**事件性质区分**：
- 已发生事件 vs 未来事件预告
- 官方政策行为 vs 官员言论
- 硬数据 vs 市场定价
- 原发信源 vs 转引

**矛盾处理**：
- 数值类矛盾以权威快照为准
- 方向性矛盾并列标注，不裁决
- 时间口径矛盾标注差异，不合并

### 4.3 输入输出

| 项 | 内容 |
|:---|:---|
| **输入** | 原始搜索结果 + 快照基准 |
| **输出** | 分级情报包（每条含：内容、来源、等级、使用建议） |

**约束**：校验阶段不生成新信息，不做结论判断，只做分级与标注。

---

## 五、阶段三：生成（Generate）

### 5.1 设计目标

- **结构化整合**：将分级情报整合为可读的结构化简报
- **信息不丢失**：所有L1/L2情报必须进入简报，不得选择性遗漏
- **矛盾不掩盖**：矛盾信息必须标注，不做统一
- **不做判断**：简报只整合情报，不做评分与结论

### 5.2 核心设计

**简报结构**：

```
1. 核心事实核查（前置）
2. 关键数据列示（快照为准）
3. 按维度分组的情报（含信源等级）
4. 对下游的影响（方向性描述，不做评分）
5. 信源盲区与待验证清单
```

**上下文精简**：
- 剔除与当前分析无关的历史情报
- 长文本只保留关键句
- 相同事件合并描述

**信息防火墙**：
- 简报层不得出现"触发/未触发/评分/阈值"等评分词汇
- 简报层不得引用框架内部术语
- 简报层不得输出操作建议

### 5.3 输入输出

| 项 | 内容 |
|:---|:---|
| **输入** | 分级情报包 + 快照基准 |
| **输出** | 结构化情报简报 |

**约束**：简报阶段是"信息整合器"，不是"判断器"。

---

## 六、阶段四：审核（Audit）

### 6.1 设计目标

- **规则触发自检**：对照规则清单逐项检查，不漏不误
- **数据一致性核验**：简报与快照逐项比对
- **逻辑方向核验**：与基线方向矛盾时拒绝采纳
- **输出可追溯**：每条结论可回溯到情报来源

### 6.2 核心设计

**强制核验步骤**：

```
第一步：数据与时间核验（逐项比对）
第二步：逻辑与状态核验（方向性常识检查）
第三步：信息质量核验（反模糊信息）
第四步：规则触发自检（硬数据优先）
```

**核验表格输出**：
- 每项关键数据必须列出"简报值 / 快照值 / 是否一致 / 处置"
- 核验结论必须明确
- 矛盾项必须在报告开头输出

**反馈闭环**：
- 审核发现的问题（如情报分级错误）反馈至校验阶段
- 重复出现的问题触发规则更新
- 规则更新进入版本归档

### 6.3 输入输出

| 项 | 内容 |
|:---|:---|
| **输入** | 结构化简报 + 快照基准 + 动态基线 |
| **输出** | 分析报告（含核验表格 + 评分 + 结论） |

**约束**：审核阶段必须输出核验表格，且表格是报告有效性的前提。

---

## 七、全链路的关键约束

### 7.1 单向数据流

```
搜索 → 校验 → 生成 → 审核
```

**禁止反向依赖**：审核阶段不得修改搜索阶段的结果，只做"使用/不使用"的决策。

### 7.2 阶段可独立替换

每个阶段有标准化输入输出接口，可单独替换实现（如更换搜索实现、更换模型），不影响其他阶段。

### 7.3 阶段可降级

任一阶段失败时的降级路径：

| 失败阶段 | 降级方式 |
|:---|:---|
| 搜索 | 保留上一份有效搜索结果 |
| 校验 | 原始搜索结果直接进入简报阶段 |
| 生成 | 保留上一份有效简报 |
| 审核 | 输出中断，不产生无效报告 |

### 7.4 阶段可审计

每个阶段输出独立保存，可追溯到具体时间点的具体内容。审计时按阶段回溯，不依赖整体日志。

---

## 八、与向量检索的关系

本系统**不依赖传统向量检索**，原因：

| 维度 | 向量检索 | 本系统方案 |
|:---|:---|:---|
| 时效性 | 依赖索引更新，滞后 | 实时搜索，当日增量 |
| 可控性 | 相似度不可解释 | 关键词可控、可验证 |
| 矛盾处理 | 无机制 | 分级标注 + 矛盾识别 |
| 降级能力 | 依赖索引 | 全链路降级 |

**但保留向量检索用于特定场景**：

- 归档记忆的按需检索（历史案例、废弃规则）
- 内部知识库的相似问题召回

**混合架构**：实时搜索为主 + 向量检索为辅，各取所长。

## 九、性能与成本优化

| 维度 | 优化策略 |
|:---|:---|
| **延迟** | 搜索实例并行；校验/生成阶段串行以保一致性 |
| **成本** | 简报阶段用轻量模型，分析阶段用重量模型 |
| **上下文** | 简报阶段精简，审核阶段注入完整规则 |
| **缓存** | 相同快照下的重复查询走缓存；快照更新后缓存失效 |

## 十、设计决策记录

### 决策 1：为什么搜索和校验分两阶段，而不是合并

**背景**：早期版本搜索后直接进入简报生成，导致低质信息被引用。

**决策**：独立校验阶段，为每条情报分级，低等级情报不进入简报核心结论。

**收益**：简报质量显著提升，LLM幻觉引用大幅减少。

### 决策 2：为什么简报不做评分

**背景**：早期简报直接输出评分建议，但简报模型不具备完整规则上下文，经常误判。

**决策**：简报只整合情报，评分交给分析引擎，两者职责分离。

**收益**：评分准确性提升，简报可复用于不同评分场景。

### 决策 3：为什么保留"信源盲区"清单

**背景**：早期简报只列出已确认信息，忽略"查不到"的部分，导致下游误以为信息完整。

**决策**：强制输出信源盲区清单，明确"哪些信息没查到"。

**收益**：下游对信息完整度有准确认知，避免基于不完整信息做决策。

### 决策 4：为什么需要审核阶段

**背景**：早期流程是"生成即输出"，缺少质量把关。

**决策**：独立审核阶段，强制核验表格、规则自检、矛盾标注。

**收益**：输出质量稳定，问题可追溯，规则可迭代。
