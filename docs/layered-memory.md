# 分层记忆机制

> 本文档描述项目的分层记忆机制的设计思路。具体规则、阈值、评分参数等核心机密不在本文档范围内。

---

## 一、为什么需要分层记忆

在长期运行的自动化分析系统中，记忆管理面临三个核心矛盾：

| 矛盾 | 表现 |
|:---|:---|
| **上下文有限 vs 历史无限** | 每轮分析都注入完整历史，上下文迅速膨胀 |
| **规则稳定 vs 规则迭代** | 每次规则更新都要改文件，历史版本被覆盖，无法回溯 |
| **状态连续 vs 版本独立** | 每日状态需要继承，但版本升级后旧状态不能直接沿用 |

**核心问题**：如果所有内容都放在活跃记忆中，系统会膨胀；如果全部遗忘，又会在遇到"以前处理过的问题"时从头再想。

**解决思路**：引入**分层记忆机制**，将"高频使用的活跃内容"和"低频使用的归档内容"分离，按需检索，兼顾效率与完整。

---

## 二、三层记忆架构

```
┌─────────────────────────────────────────────────────────┐
│  活跃记忆（Active Memory）                               │
│  · 当前有效规则                                          │
│  · 动态基线（当前状态）                                   │
│  · 最近N天的运行状态                                      │
│  → 每次分析直接注入，占用上下文                            │
├─────────────────────────────────────────────────────────┤
│  索引记忆（Index Memory）                                │
│  · 历史版本的版本号+关键词+适用场景                        │
│  · 归档内容的位置索引                                     │
│  → 不直接注入，用于检索定位                                │
├─────────────────────────────────────────────────────────┤
│  归档记忆（Archive Memory）                              │
│  · 历史版本完整内容                                       │
│  · 废弃规则与历史案例                                     │
│  · 演化决策记录                                          │
│  → 不注入，仅按需检索                                     │
└─────────────────────────────────────────────────────────┘
```

**核心原则**：**越常用越活跃，越冷门越归档。**

---

## 三、逐层设计

### 3.1 活跃记忆（Active Memory）

**职责**：存放当前直接使用的内容，每轮分析直接注入上下文。

**内容范围**：

| 类型 | 例子 | 更新频率 |
|:---|:---|:---|
| **当前有效规则** | 框架文件（最新版本） | 规则更新时 |
| **动态基线** | 昨日各维度状态与得分 | 每日 |
| **近期状态** | 最近几天触发信号、异常事件 | 每日 |

**注入策略**：

- 每次分析注入**完整但精简**的活跃记忆
- 长文本只保留当前有效的部分
- 不注入历史版本、废弃规则、历史案例

**容量约束**：

- 活跃记忆保持在可控范围内（避免上下文爆炸）
- 超出范围时，优先归档"使用频率最低"的内容

**裁剪流程**：

```
识别待裁剪内容
    ↓
评估是否仍会被使用
    ├─ 会被使用 ──▶ 移入归档记忆（带索引）
    └─ 不会使用 ──▶ 确认删除
    ↓
活跃记忆瘦身
```

**关键设计**：**裁剪不是删除，是移入潜意识。**

### 3.2 索引记忆（Index Memory）

**职责**：存放归档内容的位置索引，用于快速定位历史内容。

**内容范围**：

| 索引类型 | 例子 |
|:---|:---|
| **版本索引** | 每个版本的版本号、日期、核心更新关键词 |
| **规则索引** | 每条历史规则最初出现在哪个版本、后来如何演化 |
| **案例索引** | 历史案例（如某次危机、某次验证）的归档位置 |
| **决策索引** | 演化决策记录（为什么修改、为什么删除） |

**索引格式**（抽象示例）：

```
| 归档日期 | 内容类型 | 关键词 | 文件位置 | 触发场景 |
|:---|:---|:---|:---|:---|
| 某日期 | 旧规则 | 关键词A | archive/rules/v1#3 | 遇到规则X需要回溯时 |
| 某日期 | 历史案例 | 关键词B | archive/cases/v1#1 | 分析类似危机时 |
| 某日期 | 决策记录 | 关键词C | archive/decisions/v1#2 | 复盘规则变更时 |
```

**检索机制**：

- **第一版**：人工查索引表（简单可靠）
- **未来版本**：考虑向量检索（内容规模较大时）

**关键设计**：**索引不存放内容，只存放"内容在哪里"。**

### 3.3 归档记忆（Archive Memory）

**职责**：存放不常用但需要保留的历史内容，按需检索。

**内容范围**：

| 类型 | 说明 |
|:---|:---|
| **历史版本** | 所有历史版本的完整文件 |
| **废弃规则** | 已删除但保留的规则 |
| **历史案例** | 典型事件、验证样本、错误案例 |
| **演化决策** | 为什么修改、为什么删除、当时的判断依据 |

**存储形式**：

- 独立文件存储，不与其他内容混存
- 每个归档条目关联索引（在索引记忆中登记）
- 历史版本不修改、不删除

**检索触发**：

| 场景 | 触发方式 |
|:---|:---|
| 遇到框架未覆盖的新情况 | 人工查索引，定位归档 |
| 某个规则需要回溯 | 人工查索引，定位历史版本 |
| 历史案例需要参照 | 人工查索引，定位案例 |
| 框架决策需要复盘 | 人工查索引，定位决策记录 |

**关键设计**：**归档不是遗忘，是让记忆沉淀到可以随时唤醒的地方。**

## 四、记忆流转机制

### 4.1 从活跃到归档

**触发条件**：

- 规则被更新替代
- 内容长期未被使用
- 版本升级（旧版本整体归档）
- 上下文容量达到阈值

**流转流程**：

```
活跃记忆中的内容
    ↓
识别可归档项
    ↓
在索引记忆中登记
    ↓
移入归档记忆
    ↓
活跃记忆移除该项
```

### 4.2 从归档到活跃

**触发条件**：

- 遇到与归档内容高度相关的场景
- 检索到相关历史处理方案
- 需要复用历史案例

**流转流程**：

```
遇到触发场景
    ↓
检索索引记忆
    ↓
定位归档内容
    ↓
判断是否可复用
    ├─ 可复用 ──▶ 临时注入活跃记忆（本轮分析内）
    └─ 不可复用 ──▶ 仅作参考
```

**关键约束**：**归档内容的临时调用，不改变活跃记忆的长期状态。**

### 4.3 版本迭代时的流转

```
旧版本框架
    ↓
新版本上线
    ↓
旧版本整体移入归档记忆
    ↓
索引记忆登记新版本+旧版本
    ↓
活跃记忆中仅保留新版本
```

**关键约束**：**版本迭代不破坏历史，新旧版本并行存在。**

## 五、关键设计决策

### 决策 1：为什么不用"全量注入"或"全量删除"

**背景**：

- 全量注入 → 上下文爆炸，LLM 注意力分散
- 全量删除 → 历史问题无法回溯，重复造轮子

**决策**：分层，活跃/索引/归档三层。

**收益**：兼顾效率与完整。

### 决策 2：为什么索引与内容分离

**背景**：如果索引和内容放在一起，索引本身也会膨胀。

**决策**：索引只存"在哪里"，内容独立存储。

**收益**：索引轻量，检索快速。

### 决策 3：为什么归档内容不注入上下文

**背景**：即使归档内容是"历史"，注入上下文仍会消耗token。

**决策**：归档内容仅在触发检索时临时调用，不常驻上下文。

**收益**：上下文效率最优。

### 决策 4：为什么版本迭代不删除旧版本

**背景**：删除旧版本会丢失"为什么这样改"的证据链。

**决策**：旧版本整体归档，永久保留。

**收益**：任何历史问题都能追溯到"当时怎么想的"。

### 决策 5：为什么先人工检索、后自动检索

**背景**：自动检索需要向量库、检索策略、相关性评分，早期投入大、收益不确定。

**决策**：第一版人工查索引表，等内容规模较大后再考虑自动检索。

**收益**：早期低成本、高可靠，避免过度工程化。

## 六、记忆质量保障

### 6.1 索引准确性

- 每次归档必须更新索引，不允许"归档了但没登记"
- 索引条目必须有明确的关键词和触发场景
- 定期审计索引与实际归档内容的一致性

### 6.2 归档完整性

- 归档内容不得修改（保持历史原貌）
- 归档条目必须标明归档时间、归档原因
- 归档内容与活跃记忆的关系必须清晰标注

### 6.3 检索可靠性

- 检索结果必须标明来源（哪个版本、哪个文件、哪个条目）
- 检索到的历史内容使用前必须判断"是否仍适用"
- 历史内容与当前规则的冲突，以当前规则为准

## 七、与RAG系统的关系

**分层记忆机制**与**RAG全链路**是互补关系：

| 维度 | 分层记忆 | RAG全链路 |
|:---|:---|:---|
| **对象** | 系统自身的状态与历史 | 外部世界的实时信息 |
| **存储** | 本地文件 + 索引 | 实时搜索 + 向量库 |
| **更新** | 低频（规则迭代时） | 高频（每轮分析） |
| **检索** | 按需检索（人工/自动） | 每轮强制检索 |
| **目标** | 状态连续 + 历史可追溯 | 信息完整 + 时效准确 |

**协同点**：

- 分层记忆的归档内容可作为 RAG 的向量库来源
- RAG 检索到的历史内容可临时注入活跃记忆
- 两者共享同一套索引规范

---

## 八、适用边界

分层记忆适用于：

- 长期运行的自动化系统
- 规则持续迭代的场景
- 状态需要连续继承的场景
- 历史需要可追溯的场景

**不适用**：

- 单次运行的系统（无需记忆）
- 规则一次定型的系统（无需归档）
- 状态无延续性的系统（无需继承）
